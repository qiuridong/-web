## 3. 已确认的平台缺陷：远程失败不重试

本地执行路径 `backend/app/scheduler/executor.py` 在子进程终态后会调用 `should_retry()` 和 `scheduler.schedule_retry()`。

远程 instance 的执行路径不同：

1. 调度器只创建 `pending` run；
2. Agent poll 领取并执行；
3. `POST /api/v1/agent/runs/{id}/result` 只写终态、同步 instance、发通知；
4. 原实现没有调用 `should_retry()` / `schedule_retry()`。

因此 instance 配置中的 `max_retries=1` 对远程 Agent 结果不起作用。run `110/115` 的零 retry 子 run 已直接证明这一点。

## 4. 实施的修复

提交 `86b1ff1`（已推送 `origin/feat/script-hub`）：

- 在 `backend/app/api/v1/agent.py` 增加 `_remote_run_attempt()`，从 `trigger_type=retry` + `parent_run_id` 推导远程 run 尝试次数，并用 visited 集合防损坏父链死循环。
- Agent poll 生成 `AgentTaskPayload` 时传递真实 attempt，不再固定写 `1`。
- Agent 终态回传完成数据库写回后，按 instance 的 `max_retries` / `retry_interval_sec` 调用统一 `should_retry()` / `compute_retry_delay()`，通过面板 Scheduler 安排 retry run。
- 只有重试链结束，或结果本来不需要重试时，才发送失败通知；成功结果仍立即通知。
- 增加 `backend/tests/test_agent_retry.py`，覆盖首次 run、两级 retry 链、300 秒重试安排、成功和重试上限不安排等情况。

## 7. 后续验证与边界

- 最有价值的验证点是 2026-09-04 08:20 的 scheduled run：若首次仍在 App/任务导航阶段失败，应该在约 08:25 自动生成一个 `trigger_type=retry`、`parent_run_id` 指向首次 run 的 retry run；这会先验证平台重试修复，再观察第二次是否进入任务页。

## 10. 失败现场与最终根因

2026-09-04 10:28（Asia/Shanghai）在 UK Agent 上启动同一 `poc34`，只做启动、截图、UI hierarchy、Activity 和 logcat 采集，不填写账号、不提交验证码、不点击签到。证据保存于本机：

```text
E:\自动化录制操作\证据\dmg-diagnostic-20260904T022812Z\
E:\自动化录制操作\证据\dmg-after-close-20260904T023626Z\
E:\自动化录制操作\证据\dmg-popup-sequence-20260904T023755Z\
```

现场顺序已经明确：

1. App 先显示“初始化成功，正在跳转到 APP”；
2. 随后出现“请尽快下载 / 全新公测版上线”公告；
3. 关闭后还有“官网 / 重要公告 / 安全下载与防封指南”公告；
4. 两个公告关闭后 App 已进入正常“频道”根页，`MainActivity` 在前台；
5. 该根页的 accessibility 明确给出 `selected_tab=channel`，但当前视觉模板不把新版“频道”页识别成 `home`，因此视觉结果仍是 `unknown`；
6. v1.2.8 的 `_dismiss_announcements` 对 `unknown` 只等待，`_navigate_my` 也只会从视觉已知页点击“我的”。已有的底栏语义恢复只放在任务导航后半段，尚未覆盖冷启动和“我的”导航入口。

这与 run `121/122/123` 的 `announcement → unknown → 240 秒超时` 日志完全吻合。根因不是账号密码、验证码、ADB boot、Emulator 序列号或签到成功判定，而是 **App 公告后的新版“频道”页超出了启动视觉模板，语义证据没有在正确阶段接入**。
