# 动漫共和国管家连续失败与 v1.2.4 修复

> 日期：2026-08-26
> 范围：生产面板 instance `5` 的定时/手动失败、UK Agent 实际执行链、v1.2.4 修复与管家闭环验收
> 结论：已定位并修复。生产 run `66` 由面板创建、UK Agent 拉取执行后返回 `success`，不是 SSH 直跑脚本得到的结果。

## 1. 生产事实

面板 SQLite、Agent 日志和 UK Emulator 三方交叉核实如下：

- instance `5`：`enabled=true`，节点 `uk-9950x-android`，cron `20 8 * * *`，timeout `1200s`，`random_delay_sec=0`。
- 脚本升级前为 v1.2.3；Agent 正常在线并持续 heartbeat/poll 200，失败不是节点离线、派发丢失或超时杀进程。
- run `59`（`scheduled`）与 run `60`（`manual`）都在进入任务中心后失败：`expected=['task_ready', 'task_signed', 'task_success_dialog'] last=unknown`。
- run `64`（`manual`）在从当前页面恢复到“我的”时得到 `last=unknown`。该次没有保存逐帧图，不能单独反推最终页面；后续真实复现证明同一任务页状态平分会让“我的”导航也失去可点击的已知前置状态。
- 为排除“SSH 手动可成功、管家执行才失败”的混淆，先由面板 service 创建真实 run `65`，再由 Agent poll 领取、同步 bundle、调用 sandbox 和 Emulator。run `65` 稳定复现同一失败，`duration=130486ms`，Emulator 仍在 `finally` 中正常关闭。

## 2. 根因直接证据

run `65` 外部只读采样完整记录了生产页面状态：

1. Emulator 冷启动后进入 App，公告被状态机识别并关闭；
2. 首页判定为 `home`；
3. “我的”页判定为 `my_logged_in`；
4. 进入任务中心后，页面已有首日勾选，确实是“今日已签到”；
5. v1.2.3 分类分数连续保持：
   - `nav=0.99999958`
   - `layout=0.99803162`
   - `ready=1.0`
   - `signed=1.0`

旧逻辑要求 `ready > signed` 才是 `task_ready`，或 `signed > ready` 才是 `task_signed`。生产页面签到前后顶部“签到”圆形按钮不变，因此“已签到”页面会同时满足顶部 ready 模板和首日勾选 signed 模板；两者同为 `1.0` 时两个严格大于分支都不成立，最终错误落入 `unknown`。

这也解释了为什么 run `57` 曾成功、次日 run `59`/`60` 又失败：问题不是面板和 SSH 环境不同，而是 v1.2.3 的测试样本没有覆盖“顶部 ready 模板也精确匹配”的平分边界。

## 3. v1.2.4 实施

- 将首日勾选 `signed` 作为更具体的状态证据：
  - `signed_score >= 0.88` 时优先返回 `task_signed`；
  - 仅在没有 signed 证据时，`ready_score >= 0.88` 才返回 `task_ready`；
  - 成功弹窗仍在两者之前按独立白色面板条件判断，未放宽点击前置条件。
- 新增回归：把 ready 顶部模板原样覆盖到 signed 页面，强制制造 `ready≈1.0` 与 `signed>=0.90` 同时成立，断言必须返回 `task_signed`。
- manifest 和脚本版本升至 `1.2.4`。

涉及文件：

- `scripts/dmgongheguo/helpers/captcha_solver.py`
- `scripts/dmgongheguo/main.py`
- `scripts/dmgongheguo/manifest.yaml`
- `backend/tests/test_dmgongheguo.py`
- `脚本货架/backend/seed/scripts/dmgongheguo/` 中对应的 main、manifest 和 solver 镜像

## 6. 风险、后续与回滚

- run `66` 发生在当天已经签到之后，验证的是最常见的幂等“已签到”路径；待签到页面的离线样本仍返回 `task_ready`，点击后的三态流程未改动。下一个自然验证点是 2026-08-27 08:20（Asia/Shanghai）的 scheduled run。
- `random_delay_sec=0`，因此当前实例的 scheduled 与 manual 不存在随机延迟差异；本次根因同时出现在 scheduled run `59` 和 manager manual run `65`，修复位于二者共用的 UI 分类器。
